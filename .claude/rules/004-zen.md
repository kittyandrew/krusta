# Zen: live checks and the bench

Only Andrew's Zen is signed in to krusta's sites, so the real feed, the bench and memory are checked in a headless
Zen of krusta's own that carries a copy of his cookies for them: `tests/zen.sh`, read it once. Never drive his own
browser (keys, about:debugging, restarts): he asked for a separate instance (Oct 27, 2026). Every step is
`agentic`.

## The instance

```bash
. tests/zen.sh && zen_start            # Zen and geckodriver as user units, staged .#extension installed; ~15 s
go https://x.com/home                  # loads in the session's tab, then waits 4 s (or the seconds given)
js 'return document.title'             # a function body run in the tab; its value as JSON, promises awaited
shot home                              # $ZEN_SHOTS/home.png at 1920x1080: Read it before zen_stop
button                                 # clicks krusta's toolbar button: off or on, and the tab reloads
zen_stop                               # stops both units and deletes the profile: it holds a live session
```

- It sources from the tool's zsh and from bash. State lives in `$XDG_RUNTIME_DIR/krusta-zen`: the session id, the
  profile, downloads, Zen's TMPDIR and the screenshots (`shots/`). `zen_start <dir>` installs another build;
  `addon <dir or xpi>` adds one.
- `wd METHOD /path [json]` is any other WebDriver call in the session: `wd GET /url`, `wd GET /window/handles`.
- Each start is a fresh profile with only the cookies of each site's `hosts` (and their dot domains) from the
  profile Andrew uses (the newest `cookies.sqlite` under `~/.zen`). The system policies still apply: his add-ons
  and bookmarks load there too.
- After a rebuild, `zen_start` again. Another session's instance shares the units: check
  `systemctl --user is-active krusta-zen` first.

kitter's pages to check: the bar's tabs (For you, Following, a pinned list), a profile with a banner such as
`x.com/XDevelopers` and one without, a video, a photo's viewer.

## kitter's bench and memory (docs/design.md, Against x.com)

`sites/kitter/tests/bench/run.sh` starts the instance, installs its folder beside krusta and runs `memory.py`
against it. It prints both reports and copies them to `~/.local/state/krusta-dev/bench-results/`. It takes
about six minutes, so run it as a unit and read the log after:

```bash
systemd-run --user -q --unit=kitter-bench --collect -p MemoryMax=2G --working-directory="$PWD" \
  bash -c 'sites/kitter/tests/bench/run.sh >/tmp/kitter-bench.log 2>&1'
```

Add each run to the doc's tables with its date; never replace one quietly: x.com's numbers swing between runs.
Try any signal but memory.py's 34 on a throwaway instance first: a signal Zen does not handle kills it.

## Comparing with a fresh Firefox

To tell kitter from the browser, run the same snippet in Firefox through Selenium (`nix shell --impure --expr`
with `firefox`, `geckodriver` and `python3.withPackages [selenium]`), as `sites/kitter/tests/budgets/budgets.py`
does.

## Traps seen here

- x.com's own app logs the copied session out after about 3.5 minutes of use (five loads with a scroll): the next
  load lands on `/?logout=<ms>` and every x.com cookie is gone. kitter alone ran 25 loads without it; copying
  x.com's site storage or closing Andrew's Zen did not help, and his own session stayed valid (Oct 27, 2026).
  The bench's third memory round hits it.
- geckodriver rejects Zen's binary: Zen starts with `--marionette` and geckodriver `--connect-existing`.
- Zen opens `cookies.sqlite` in exclusive mode: a copy opens only with `PRAGMA locking_mode = EXCLUSIVE`, and a
  running Zen's copy not at all. `profiles.ini`'s `[Install]` default named a profile unused since 2025.
- A kitter page never fires `load`: the session uses the "none" page-load strategy, and `go` waits instead.
- Zen differs from Firefox for the toolbar button: it calls `action.onClicked` with no tab from its extensions menu
  and reports updates of a tab -1. vm-kitter runs Firefox, so check a button change here too (`button`).
- Requests wait 170 to 530 ms before they are sent, on new connections, in Andrew's Zen and in the instance
  alike; a fresh Firefox waited 0 to 60 ms. Cause not found (docs/design.md, Against x.com).
